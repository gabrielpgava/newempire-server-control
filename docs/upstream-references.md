## Compatibility and trust notes

- Fetch version lists rather than copying example Minecraft/Fabric/Java versions from upstream prose. Query failures must remain visible; do not fall back to invented current versions.
- Modrinth project IDs, version IDs, hashes, declared loader/game/environment support, dependencies, and file origins are different checks. Filename matching is not inventory identity; an unknown hash is not permission to replace an external file.
- Verify published hashes where available. For Fabric's generated launcher, distinguish official HTTPS-origin trust and local staging integrity from an independently published checksum/signature. First-launch bootstrap downloads also require separate operational scrutiny.
- HTTP download URLs and redirects must remain within the application's allowlists/public-network restrictions. Provider documentation does not authorize access to localhost, private networks, arbitrary mirrors, or inherited proxy settings.
- GitHub release notes, tags, checksums without authentication, and an asset's `digest` alone are not a complete updater trust chain. A missing official signing key or privileged helper is an actionable blocker, not a reason to accept an unsigned update.
- API documentation can change independently of installed dependency versions. Recheck these references when updating runtime, content, tus, or release code and record actual live-test evidence in [acceptance](acceptance.md).
